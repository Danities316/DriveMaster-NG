1. Product Vision
DriveMaster NG is an offline-first PWA for Nigerian driving schools. It is designed to reduce cash leakage, improve visibility into student payments, control vehicle/fuel claims, manage driving-session scheduling, and generate dynamic WhatsApp receipts.
The product must remain useful under intermittent 2G/3G connectivity and dead zones. Local-first operation is a core product requirement, not merely an implementation detail.
2. Product Principles
Offline-first: local IndexedDB is the immediate operational source of truth.
Network agnostic: core workflows must continue when the internet is unavailable.
Zero data loss goal: user actions are persisted locally before synchronization.
Human-controlled architecture: high-level architecture, schemas, state boundaries, APIs, and business rules remain under human governance.
Bounded AI implementation: Claude AI implements independently testable units and must not redesign architecture without approval.
Mobile-first: optimize for low-cost Android devices and outdoor/daylight use.
Simple operations: common actions should require minimal steps and clear feedback.
MVP discipline: only features required to validate the core product proposition belong in the 30-day MVP.

7. MVP User Journeys
7.1 Register Student
Authorized staff opens the student registration workflow.
Staff enters required student information and tuition amount.
App validates the input.
Record is written to IndexedDB first.
UI updates immediately.
A CREATE mutation is added to the outbox.
When connectivity is available, the mutation is synchronized with the backend.
7.2 Record Payment
Staff opens the student record.
Staff records payment amount and payment mode.
Payment is persisted locally first.
Student balance updates immediately.
Payment mutation enters the outbox.
A dynamic WhatsApp receipt link is generated.
7.3 Book Driving Session
Staff selects student, vehicle, and session time.
System checks for an overlapping booking for the selected vehicle.
If a conflict exists, creation is blocked.
If valid, the booking is persisted locally and queued for synchronization.
7.4 Record Fuel
Authorized staff records vehicle, odometer reading, and fuel cost.
System compares the reading against the relevant previous odometer value.
The discrepancy rule is evaluated.
The fuel log is stored locally first.
If suspicious according to the approved rule, a visible alert is generated.
7.5 Synchronize
App detects network availability.
Pending mutations are processed sequentially.
Server acknowledges processed mutation IDs.
Successful mutations are marked complete/removed from the active outbox.
Failed mutations remain recoverable and retryable.

10. Core Business Rules
10.1 Ledger Balance Integrity
Student.balanceRemaining = Student.totalTuition − Σ(Payment.amount).
10.2 Schedule Conflict Guard
A SessionBooking cannot be created if the selected vehicle has an overlapping start-time + duration window.
The exact duration field/value must be established before implementation.
10.3 Fuel Discrepancy Flagging
The source PRD currently states that a FuelLog triggers discrepancyAlert = true if the distance delta between odometer readings is less than 10 km per ₦5,000 fuel claimed. The exact mathematical interpretation is ambiguous and must be approved before Claude implements the rule.
No AI agent may reinterpret this rule without Product Owner approval.

11. Offline-First Architecture
All core reads and writes resolve against local IndexedDB before asynchronous background synchronization.
React/UI layer binds to local data.
Dexie/IndexedDB is the local source of truth for immediate operations.
Local writes optimistically update the UI.
Mutations are appended to a durable outbox.
A sync controller processes pending mutations when connectivity is available.
The cloud backend provides durable synchronization and cross-device persistence.
Reference flow: UI Action → Dexie write → optimistic UI update → Outbox Queue → Sync Controller → HTTPS REST Backend.
12. Sync Protocol
The current synchronization endpoint is POST /api/v1/sync/batch.
Mutation structure:
id: UUID v4
entity: student | payment | booking | fuel_log
action: CREATE | UPDATE | DELETE
payload: entity payload
timestamp: epoch milliseconds
status: PENDING | SYNCING | FAILED
retryCount: integer
The current response contract includes success, processedIds, and conflicts.
12.1 Required Sync Decisions Before Production
Idempotency: duplicate delivery of the same mutation must not create duplicate records.
Conflict resolution: define behavior when the same entity is changed on multiple devices while offline.
Retry policy: define retry timing, maximum attempts, and FAILED-state handling.
Authentication of synchronization requests.
Device identity and device registration.
Behavior when a device is offline for an extended period.
Behavior after local database reset or application reinstall.
These are mandatory architecture decisions because offline-first is a core product requirement.

26. Locked Architecture & Product Decisions — v1.2
This section converts the open decisions identified in PRD v1.1 into binding MVP requirements. These decisions are now part of the DriveMaster NG source of truth. Claude AI must implement them as specified and must not reinterpret them without explicit approval from the Founder/Product Owner.
26.1 Authentication
MVP authentication uses conventional credential authentication: phone number or email plus password.
OTP login is deferred to post-MVP to avoid SMS cost and delivery dependencies.
Authenticated sessions/tokens must be implemented using a secure server-approved mechanism.
Long-lived authentication secrets must not be stored insecurely in ordinary localStorage or IndexedDB.
26.2 School / Multi-Tenant Model
DriveMaster is modeled as a multi-tenant SaaS application.
A School/Tenant entity is required.
Tenant-owned records must contain schoolId.
The backend derives the school/tenant from the authenticated user/session; client-supplied schoolId is never trusted for authorization.
Tenant ownership must be enforced at the service/data-access layer for every tenant-owned resource.
Shared PostgreSQL database with tenant-scoped records is the MVP architecture.
26.3 MVP Roles
Owner: full school-level visibility and management.
Receptionist: student management, payment recording, booking management, receipt generation, and relevant operational viewing.
Instructor: assigned-session and relevant student/vehicle access; may update session status.
Owner-only controls must not be exposed to Receptionists or Instructors.
Backend authorization is mandatory; UI hiding alone is not security.
26.4 Session Booking Model
SessionBooking must include instructorId and durationMinutes.
Default session duration is 60 minutes, while the booking workflow may allow a different duration.
Booking status values are SCHEDULED, COMPLETED, CANCELLED, and NO_SHOW.
Vehicle conflicts are blocked when time windows overlap.
Instructor conflicts are also blocked for overlapping time windows.
Overlap rule: existing.start < new.end AND existing.end > new.start.
26.5 Fuel Discrepancy Rule
For MVP, discrepancyAlert is true when distance delta is less than 10 km AND fuelCost is greater than or equal to ₦5,000.
distanceDelta = currentOdometer - previousOdometer.
The MVP must not attempt to infer fuel efficiency or accuse a vehicle based on a universal consumption rate.
Vehicle-specific fuel-efficiency intelligence is deferred to post-MVP.
26.6 Conflict Resolution
Financial transactions such as payments and fuel logs are append-only and must not be silently overwritten.
Non-critical profile fields may use version-aware last-write-wins behavior.
Bookings use server-side conflict detection. If two devices create overlapping bookings for the same vehicle or instructor, the server accepts one valid mutation and returns a conflict for the other.
Conflict responses must be represented explicitly in the local outbox state as CONFLICT.
The client must not silently resolve financial or scheduling conflicts.
26.7 Idempotency
Every outbox mutation has a globally unique mutationId (UUID v4).
The backend records processed mutation IDs.
Repeated delivery of an already processed mutation must not create a duplicate business record.
The synchronization response must communicate already-processed/duplicate mutation IDs where applicable.
26.8 Retry Policy
Outbox states are PENDING, SYNCING, FAILED, and CONFLICT.
Automatic retry schedule: immediate, then approximately 5 seconds, 30 seconds, 2 minutes, and 10 minutes.
After five unsuccessful attempts, the mutation becomes FAILED and remains stored for recovery.
Failed mutations must not be deleted automatically.
The UI must show when unsynchronized mutations remain.
26.9 Bidirectional Synchronization
Synchronization is bidirectional: device PUSHes local mutations to the server and PULLs server changes.
Sync sequence: push pending mutations → receive acknowledgements/conflicts → pull changes since last sync cursor → apply changes locally → advance cursor.
Use a server-generated change cursor/version for incremental pull rather than relying solely on device clocks.
The local database remains the immediate operational source of truth while the server provides durable persistence and cross-device synchronization.
26.10 Device Identity
Each app installation receives a persistent deviceId.
Mutations carry mutationId and deviceId.
Device identity is used for synchronization, diagnostics, and auditability.
26.11 Local Data and School Switching
Only one school account is active in a device session for MVP.
When switching schools, the previous school's tenant-scoped local operational data must be cleared before the new school is initialized.
A user must never be able to see another school's locally cached records after switching accounts.
26.12 Reinstall / Unsynchronized Data
Unsynchronized local mutations may be lost if the application is removed or local storage is destroyed.
The application must clearly warn users when unsynchronized mutations remain.
The cloud backend is the durable recovery source after successful synchronization.
26.13 Audit Trail
A lightweight AuditLog entity is included in MVP.
Minimum fields: id, schoolId, userId, action, entity, entityId, timestamp, metadata.
At minimum, important student, payment, booking, and fuel actions must be auditable.
Financial records should be corrected through traceable correction events rather than silently erasing history.
26.14 Financial Transaction Integrity
Payments are immutable/append-only for MVP.
A mistaken payment is corrected through a compensating/correction transaction rather than destructive editing.
Fuel logs follow the same historical integrity principle.
The student's balance is derived from the tuition amount and valid payment transactions.
26.15 API / Data Governance
APIs must preserve approved entity names, identifiers, request shapes, response shapes, and synchronization semantics.
Claude AI must not silently change schemas or API contracts.
Any architecture change affecting tenant isolation, synchronization, domain rules, or financial integrity requires Founder/Product Owner approval.
27. Final MVP Architecture
The approved architecture is a local-first React PWA backed by Dexie/IndexedDB, a durable outbox, a synchronization controller, HTTPS APIs, and a multi-tenant PostgreSQL backend.
Operational flow: UI action → local Dexie persistence → optimistic UI update → durable outbox → synchronization controller → backend idempotency/validation/conflict handling → acknowledgement → incremental pull → local application of server changes.
